# Stage 0 detail: the prompt, the modifiers and the pre-flight

Steps 5, 6 and 8 of Stage 0 in `SKILL.md`, in full. Read this when you reach step 5.

## Step 5. The prompt

Write the prompt in `.100x/project.md`. The brief is a few lines, so first read what it names, what is already here and what the owner built that is alike. Then write the longer prompt the owner would have written: the brief word for word, the goal, what you read first, the rules, the riskiest unknown, the **Asks** ledger with a proof ask for each claim the stages cannot see, the scope, the test material, what not to do, the assumptions you made instead of asking, the one thing that must not break and its kind (`references/must-not-break.md` lists the kinds), the properties of the part with logic (`references/properties.md`: state, transitions, preconditions, postconditions, invariants and liveness, or `none: <reason>`), the moment, and the judge focus. Add the stack, the run command, and the modifiers in effect. `references/prompt.md` says how and `references/prompt-example.md` shows two. Run `100x prompt check` and fix what it names. Take about 15 minutes, plus the reading the brief names. The question from "When you are not sure" comes before this step, so inside the prompt you decide and log, and never ask.

## Step 6. Modifiers

Modifiers. `3 versions` runs `100x config set variants.count 3 --local` and reads `references/variants.md`. `5 rounds of judging` runs `100x config set review.rounds 5 --local`. `max 5 subagents` runs `100x config set subagents.atOnce 5 --local`. A length of work (`for 10 hours`, `for 2 days`, `until 6am`) means use all of it: run `100x clock set "<the owner's words>" --fill`, for example `100x clock set "for 10 hours" --fill`, and arm the watchdog, see `references/watchdog.md`. Call the skill the way your app does when you tell the owner what to say, `/100x` in Claude Code and Cursor and `$100x` in Codex. `no verification` runs `100x config set verify.enabled false --local`, and then the prompt has no Properties section and the final message says nothing was verified. Property checks are on otherwise, whatever the owner's global setting says unless it is `false`. Record every number phrase in effect under Modifiers in `project.md`. Add `Mode: overnight` when `100x-overnight` sent you here, and `Grind: yes` when `100x-grind` did, and then run `100x config set review.grind true --local`.

## Step 8. The pre-flight

Send the pre-flight, at most 12 lines, and keep working. Start every line with its label (`Goal:`, `Asks:`, `Moment:`, `Riskiest:`, `Must not break:`, `Phrases:`, `Time:`, `Assuming:`, and `Call` for the lines that say what to call) so the eye finds a line without reading the rest. One line each for the goal in your words, the number of asks, the moment, the riskiest unknown, the one thing that must not break, the number phrases in effect, and the time it takes. That is seven lines. The must-not-break line also says what will be checked, so the owner sees it before the build: when property checks are on, how many properties the plan holds and that they are checked and recorded in `verify/ledger.tsv` by stage 5 ("4 properties, checked at stage 5"), or `none` with the reason and that the code will be waived with `100x verify waive`; when they are off, "property checks off, nothing verified". The time line lets the owner pick the commitment before the run takes it: a normal run takes hours, because every polish pass and every round of judging is another model at work, and `100x-mockup` is the fast way, about fifteen minutes and no judges. A grind has no end time, and its time line says what stops it. Then the assumptions, at most three, one per line. Then one or two "call X to change Y" lines, and `100x-setup` for the models and their jobs is always one of them. That makes 12 lines at most, so a model line, when one applies, takes the place of the third assumption. When `100x config target builder` prints a model (`{}` means this thread's own model, so there is nothing to compare) and your app shows this thread on another model or a lower effort, say so and which model the owner prefers, then carry on without waiting. When `100x doctor --json` shows the `judge` check as a warning because the judge is the model that builds, the model line says that too: the review would be a self-review, and `100x-setup` changes it. The watchdog line (`references/watchdog.md`) joins the number phrases line. Paste the sent lines under `## Pre-flight` in `.100x/project.md`.
